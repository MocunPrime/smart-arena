# 多棋种赛事规则与智慧赛场 —— 设计文档

> 本文档面向毕业论文写作，系统性地说明“多棋种赛事规则与智慧赛场”的需求来源、
> 总体架构、模块设计与关键算法，并给出与代码文件、类名的对应关系，便于直接引用。

---

## 1. 项目背景与目标

### 1.1 背景

当前主流棋类软件（如本项目参考的 Katayzy）以**围棋单机 AI 分析**为核心：加载引擎、
显示胜率、给出推荐点。但针对“**线下多棋种赛事**”这一场景，仍然缺少一套完整的支撑软件：

- 只能下围棋，无法同时支持五子棋、翻转棋；
- 没有**面向裁判**的犯规记录与判罚逻辑；
- 没有**团队赛制**（分阶段上场、集体投票决策）；
- 家长无法在场外实时观赛，缺少**智慧赛场**方案；
- 缺少与**实体棋盘 / 硬件**（树莓派、OLED、传感器）的对接。

### 1.2 目标

在 Katayzy 的基础上，设计并实现一套**多棋种赛事规则与智慧赛场系统**，目标为：

1. **多棋种**：围棋、五子棋、翻转棋统一抽象，规则可插拔；
2. **赛事裁判**：覆盖犯规判罚、计时、弃权记录、终局汇总；
3. **团队赛制**：实现“足球式”分阶段上场与加权投票决策；
4. **智慧赛场**：局域网内家长扫码实时观赛（棋盘 + 胜率）；
5. **硬件与部署**：提供三种可落地部署方案的软件接口。

## 2. 需求分析

需求来源于导师与学生的会议讨论（见 `docs/会议记录-原始转写.txt`）。提炼为如下功能需求：

| 编号 | 需求 | 来源要点 |
| --- | --- | --- |
| R1 | 支持围棋、五子棋、翻转棋三种棋 | “就这三种就够了，你把它涵盖进去” |
| R2 | 非法落子“弹窗 + 音效”提示 | “第一个打结要有声音” “第二个是弹窗，然后音效” |
| R3 | 禁入点、打劫非法落子不允许下 | “不找劫财的话……就是去提劫，要不不允许他下” |

| R11 | 对接 KataGo / GTP 引擎 | 参照 Katayzy 的引擎对接 |

## 3. 系统总体设计

### 3.1 分层架构

系统自下而上分为四层，层间通过明确的接口解耦：

```
┌───────────────────────────────────────────────────────────┐
│  展示层  venue/  (HTTP + SSE + 前端)  ·  hardware/ (OLED)   │
├───────────────────────────────────────────────────────────┤
│  应用层  tournament.py (多桌赛程) · team.py (团队赛制)       │
├───────────────────────────────────────────────────────────┤
│  领域层  referee.py (裁判) · rules/ (棋种规则)              │
├───────────────────────────────────────────────────────────┤
│  基础层  model.py (领域模型) · ai.py (引擎适配)             │
└───────────────────────────────────────────────────────────┘
```

- **基础层**：定义与棋种、引擎无关的通用类型（颜色、着法、犯规、胜负）。
- **领域层**：`RuleSet` 封装单一棋种的规则；`Referee` 在规则之上叠加赛事判罚。
- **应用层**：`Tournament` 管理多张棋桌与事件总线；`team` 实现团队赛制。
- **展示层**：`VenueServer` 把状态以 HTTP/SSE 暴露给浏览器；`hardware` 驱动 OLED 与实体棋盘。

### 3.2 数据流

```
落子请求 ──► Referee.play ──► RuleSet.play ──► 更新棋盘/胜负
                 │
                 ├─► 非法 → 生成 FoulRecord → 警告 / 判负
                 └─► 合法 → 发事件(move) → EventBus ──► VenueServer(SSE) ──► 家长手机
                                                  └─► HardwareHub ──► OLED / 实体棋盘
```

关键点：`Referee` 只产生**事件**，不直接操作 UI。音效、弹窗、OLED 显示等都由订阅事件
的展示层完成，从而做到“判罚逻辑”与“呈现方式”解耦。

## 4. 领域模型设计（model.py）

| 类型 | 说明 | 与 Katayzy 对应 |
| --- | --- | --- |
| `Color` | 黑/白/空，提供 `opposite`、`name_cn` | `Stone` 枚举 |
| `GameType` | 围棋/五子棋/翻转棋 | 新增 |
| `MoveResult` | 单次落子结果（OK/自杀/打劫/禁手…） | — |
| `FoulType` | 犯规类型（含中文名） | 新增 |
| `Verdict` | 胜负（黑胜/白胜/和/进行中） | — |
| `Move` | 一步着法，可表示 pass | `BoardData` 中的落子 |
| `FoulRecord` | 犯规记录（类型、手数、时间、备注） | 新增 |

`RESULT_TO_FOUL` 建立“落子结果 → 犯规类型”的映射，是裁判判罚的统一入口。

## 5. 规则引擎设计（rules/）

### 5.1 抽象基类 `RuleSet`

所有棋种继承 `RuleSet`，统一实现：

- 棋盘访问：`get/set/cells/neighbors/in_bounds`；
- 连通块与气：`group_and_liberties`（围棋、五子棋共用）；
- 落子入口：`play`（校验回合 → 执行 → 判定胜负）；
- 合法性：`is_legal` / `is_legal_pass` / `legal_moves`；
- 计分与视图：`score` / `to_public_dict` / `extra_public`。

`_apply`、`_after_move`、`_update_verdict` 为子类预留的扩展点，实现**模板方法模式**。

### 5.2 围棋（go.py）

- **合法性**：越界、占用、**禁入点（自杀）**、**打劫（简单劫）**；
- **提子**：落子后先提对方无气块，再判自己是否自杀；
- **计分**：中国规则数子法（`_area`），含贴目 `komi`；
- **终局**：双方连续停一手（pass）进入终局并计算胜负。

算法要点：`_simulate` 在棋盘副本上试下，`_flood` 用洪水填充求连通块与气。

### 5.3 五子棋（gomoku.py）

- **胜负**：横/竖/两斜任一方向**连成五子**即胜；
- **黑方禁手**：长连（overline）、四四、三三（`_black_forbidden`）；
- **线型分析**：把每个方向转为字符串（`_line_str`），用 `_max_run` / `_is_open_three`
  / `_is_four` / `_is_open_four` / `_winning_points` 判断。

边界处理要点：棋盘外使用独立哨兵 `"#"`（而非白子 `"O"`），避免边缘被误判为“活四/五连”。

### 5.4 翻转棋（reversi.py）

- **初始局面**：标准 8×8 开局（中央黑白交错四子）；
- **合法性**：必须能翻转对方棋子（`_flips`）；
- **翻转**：在落子**之前**计算可行翻转方向，落子后统一变色（避免顺序错误）；
- **跳过**：一方无子可下时自动 pass；
- **终局**：双方都无法落子，按**子数多者胜**判定。

### 5.5 注册表（rules/__init__.py）

`REGISTRY` 把 `GameType` 映射到规则类，`create_rules(game_type, size, **kwargs)` 统一创建，
`DEFAULT_SIZE` 给出各棋种默认棋盘（围棋 19、五子棋 15、翻转棋 8）。新增棋种只需注册即可。

## 6. 裁判模块设计（referee.py）

`Referee` 在 `RuleSet` 之上实现赛事管理：

- **犯规判定**：把 `MoveResult` 通过 `RESULT_TO_FOUL` 转成 `FoulRecord`，累加计数；
  `foul_limit=2` 时，第 2 次犯规 `loss_by_foul=True`，直接判负（对应 R4）。
- **事件通知**：每次落子/犯规/停手都 `_emit` 事件（供音效、弹窗、SSE 使用，对应 R2）。
- **弃权记录**：`play_pass` 记录 `pass_order`，可回答“谁先弃权”（对应 R5）。
- **计时**：`TimeControl(total, per_move)`；`tick()` 累计用时，`check_timeout()` 把超时
  转成 `FoulType.TIMEOUT`。
- **终局小结**：`summary()` 汇总胜负、犯规列表、弃权顺序、最后一手、比分；
  `to_public_dict()` 输出可序列化视图供前端展示（对应 R5）。

## 7. 团队赛制设计（team.py）

对应 R6–R8，实现“足球式”团队赛：

- **名册 `Member`**：含角色、`weight`（投票权重）、`is_captain`、`is_guest`；
- **分阶段上场 `PhaseRule`**：按手数区间切换上场名单（开局→前锋、中盘→中场、收官→后卫）；
- **加权投票 `VotingSession`**：`cast()` 记录投票，`tally()` 按 `weight` 汇总并排序；
  队长可直接 `captain_choose()` 决定落点；
- **限时与强制**：`timeout_s` 到时 `is_expired()` 为真，`resolve()` 以
  `forced_point()`（加权最高票）强制落子（对应 R8）；
- **提醒**：`should_remind()` 在临近时限提醒队长决定。

**权重设计**：`demo_side()` 给队长 3.0、嘉宾 2.0、普通队员 1.0，且可随时调整；
符合会议“队长/嘉宾权重更高、可随时改”的要求。

## 8. AI 分析设计（ai.py）

- **`GtpClient`**：跨平台 GTP 子进程通信，后台读线程 + 队列，正确处理
  `= body` / 多行响应 / 空行分隔，支持 `close()` 优雅退出；
- **`KataGoEvaluator`**：优先调用 KataGo 的 `kata-analyze` / `kata-genmove_analyze`
  取得胜率；引擎缺失或异常时自动降级；
- **`HeuristicEvaluator`**：纯逻辑启发式（子力、中心、气等），保证**无引擎也能运行**，
  用于演示与单元测试；
- **坐标转换**：`coord_to_gtp` / `gtp_to_coord` 处理 GTP 坐标（跳过字母 I）。

`make_evaluator(engine_path)` 是统一工厂：有引擎走 KataGo，无引擎走启发式（对应 R11）。

## 9. 智慧赛场设计（venue/）

对应 R9。核心是**局域网自组网 + 扫码观看**，不依赖外网与手机卡：

- **`VenueServer`**：基于标准库 `http.server` 的多线程 HTTP 服务；
- **大厅页 `/`**：展示各桌缩略信息 + 服务地址**二维码**；
- **单桌页 `/table/<n>`**：实时棋盘（坐标标注、最后一手高亮）+ 双方胜率曲线 + 团队投票面板；
- **SSE `/events`**：服务器推送 `move` / `foul` / `state` 等事件，前端无刷新更新；
- **二维码 `qr.py`**：基于纯 Python 的 `segno` 生成 SVG/PNG/终端二维码；
- **接口 `/api/tables`、`/api/table/<n>`、`/api/play`、`/api/newtable`**：供前端与裁判端调用；
- **投票接口 `/api/table/<n>/vote/{open,cast,captain,resolve,cancel}`**：开启 / 投票 / 队长裁决 / 结算 / 取消团队投票；
- **`state` 事件**携带 `history`（手数 + 黑方胜率），前端据此绘制胜率曲线。

`local_ip()` 自动探测本机局域网地址，用于生成二维码；`advertised_host` 可手动覆盖。

## 10. 硬件接口设计（hardware.py，预留 / 暂缓实现）

> 说明：本阶段聚焦软件部分，硬件（智慧棋盘）**暂缓实现**，仅保留接口占位；跟踪见 docs/OPEN-ISSUES.md 的 ISSUE-001。以下为预留设计。

对应 R10，提供三类抽象接口：

- **显示 `OledDisplay` / `MemoryDisplay`**：把胜率、比分、桌号输出到 OLED 屏幕（含内存实现，
  便于无硬件测试）；
- **棋盘桥 `BoardLink`**：`MockBoardLink`（模拟）、`SocketBoardLink`（WiFi 棋盘，TCP/IP）、
  `SerialBoardLink`（树莓派 / 串口）；
- **`HardwareHub`**：统一订阅赛事事件，驱动显示与实体棋盘，实现软件与硬件联动。

### 三种部署方案

| 方案 | 组成 | 适用 |
| --- | --- | --- |
| A. 树莓派 | 树莓派 + 串口/GPIO + OLED | 一体化、便携 |
| B. PC + 蓝牙 | PC 做服务器，蓝牙连实体棋盘 | 场地已有电脑 |
| C. WiFi 棋盘 + 主机 | ESP/开发板 WiFi 上报，主机开热点 | 家长扫码观赛 |

三者共用同一套软件接口，仅 `BoardLink` 实现不同。

## 12. 关键技术点与创新

1. **规则可插拔**：以 `RuleSet` 模板方法统一多棋种，新增棋种成本极低；
2. **判罚与呈现解耦**：裁判只发事件，音效/弹窗/SSE/OLED 各自订阅；
3. **引擎可选**：KataGo 优先、启发式兜底，保证任何环境都能运行；
4. **零依赖 LAN 观赛**：标准库即可开服，手机扫码即看，适配偏远无信号场地；
5. **团队赛制数字化**：把“分阶段上场 + 加权投票 + 超时强制”落到可计算模型。

## 14. 死活题改卷设计（study/）

> 需求补充："软件要有改卷功能，即人做死活题，卡塔狗计算人类落子的胜率。如果连续几手的胜率在
> 90% 以上，就判断做对了；找一系列不同难度的死活题内置进去。"

### 14.1 数据结构

- **题库**（`arena/study/problems.py`）：每题含 `board`（`X`/`O`/`.` 字符画）、`solver`（行棋方）、
  `target`（要被提的目标白棋点）、`lines`（黑白交替的**参考解答线**，一到多条）。内置 8 题，
  覆盖 **入门 / 初级 / 中级 / 高级**；
- **做题会话**（`arena/study/quiz.py` `QuizSession`）：持有 `GoRules` 棋盘、把参考解答线合并成
  字典树（`_Trie`）逐手匹配，跟踪 `streak`（连续做对）、`streak_needed`（本题关键手数）、`history`。

### 14.2 判定算法

1. 人类每落一手：先校验合法性，再查该点在参考解答树中的子节点；
2. **命中正解**：本手"胜率"记为 `min(0.99, 0.92 + 0.02*streak)`（≥阈值 0.90），`streak += 1`，
   随后**自动替对手应一手**（按解答线）并继续对局；
3. **未命中**：本手"胜率"记为 ~0.30，`streak` 清零；
4. 当目标白棋被提且 `streak >= streak_needed` 时判 `solved=True`（做对）。

> 说明：棋盘局部死活直接套全局胜率无意义，故默认用"是否踩在正解树上"模拟引擎胜率；
> 已为 `StudyManager(evaluator=...)` 预留接口，可换成 **KataGo 真实胜率**（见 ISSUE-005）。

### 14.3 弃权记录（对弈侧，配合 R12）

- `Referee.play_pass()` 每次成功停一手都写入 `pass_log`，记录 `after_move_no / after_color`
  （即"这一手是在谁的哪一手之后发生的"），并以 `pass_order[0]` 给出**第一个弃权方**；
- 对局页 `#passlogbtn`（`game.js showPassLog()`）随时弹出弃权明细；终局弹窗显示 `first_pass`。
